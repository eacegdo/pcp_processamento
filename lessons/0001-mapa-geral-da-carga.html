Aula 0001 · Missão: explicar e operar a carga

Mapa geral da carga OCE

Um desenho mental para você contar ao time — e para saber onde olhar quando a carga rodar. Folha rápida: referência do mapa.

O que este sistema é

Um serviço Go que recebe um Lote OCE (CSV), cria um Job de Aplicação e atualiza a Situação OCE de Escolas já existentes no Supabase. O Bubble acompanha o progresso lendo a tabela oce_job — não precisa de GET de status na API Go. Fonte de linguagem: CONTEXT.md. Operação: README.md.

O caminho da carga (mapa)

  1. Entrada Chamador autorizado (Bubble/curl) manda o CSV em POST /v1/lotes com header X-API-Key. Código: internal/httpapi.
  2. Parse O CSV vira lista de itens (`,` ou `;`; última duplicata de INEP vence; linha incompleta ignorada). oce_status_final → Status OCE (oce_status). Código: internal/lote.
  3. Fila Nasce um Job queued. O worker pega um por vez (FIFO), marca running, aplica em batches, atualiza processadas, termina em success ou failed. Código: internal/worker + JobStore.
  4. Supabase Metadados/progresso do Job → tabela oce_job. Situação OCE → escola só em 3 colunas, via RPC aplicar_situacao_oce_lote (UPDATE em lote; sem criar Escola). Código: internal/supabase. SQL: docs/sql/.
  5. Observação Bubble lê oce_job (status, total, processadas, restantes, erro). A API Go já respondeu o id do Job na criação — a carga continua em background.
Uma frase para o time: “Mandamos o CSV, pegamos o id do Job, o worker aplica em batches no Supabase, e acompanhamos a fila em oce_job.”

O que este mapa deliberadamente não cobre

  • Pause/continue — itens do CSV ficam na memória do processo; se cair no meio, reenvia o CSV.
  • Criação de Escola — INEP inexistente é ignorado (no-op).
  • Storage do arquivo — parse na hora; CSV é temporário.

Detalhes de escopo: spec.md.
